2. Especificación
-----------------

**Declaración:**

   El sistema DEBE actualizar únicamente los campos modificados en la
   base de datos CUANDO las validaciones han sido exitosas.

**Descripción:**

   El proceso de actualización:
   
   1. Construye UPDATE solo con campos modificados
   2. Actualiza ``updated_at = NOW()``
   3. Actualiza ``updated_by = ID del admin``
   4. Si se cambió respuesta de seguridad, hashea antes de guardar
   5. Si se cambió estado a INACTIVE, guarda motivo
   6. Ejecuta en transacción atómica
   
   **Campos Actualizables:**
   
   - full_name
   - email
   - status
   - security_question
   - security_answer_hash
   - deactivation_reason (si aplica)

----

3. Criterio de Aceptación
-------------------------

::

   DADO validaciones exitosas de campos modificados
   CUANDO el sistema actualiza la BD
   ENTONCES solo los campos cambiados se actualizan
   
   Escenario 1: Actualización parcial
   DADO solo nombre modificado
   CUANDO se ejecuta UPDATE
   ENTONCES solo cambia full_name y updated_at/by
   Y otros campos permanecen intactos
   
   Escenario 2: Cambio de respuesta seguridad
   DADO nueva respuesta de seguridad ingresada
   CUANDO se actualiza
   ENTONCES se almacena el hash, no texto plano
   
   Escenario 3: Desactivación con motivo
   DADO cambio de status a INACTIVE
   CUANDO se actualiza
   ENTONCES status = 'INACTIVE'
   Y deactivation_reason contiene el motivo
   Y deactivated_at = NOW()
   
   Escenario 4: Timestamps automáticos
   DADO cualquier actualización exitosa
   CUANDO se completa
   ENTONCES updated_at = momento de actualización
   Y updated_by = ID del admin que modificó

----

4. Reglas y Restricciones
-------------------------

- **BR aplicables:** Ninguna específica
  
- **CNST aplicables:**
  - CNST-002: Gestión de datos en BD

**Concurrencia:**

Usar optimistic locking con campo ``version`` para detectar
modificaciones concurrentes y evitar pérdida de datos.
