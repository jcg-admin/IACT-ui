2. Especificación
-----------------

**Declaración:**

   El sistema DEBE cambiar el estado del usuario a INACTIVE y registrar
   el motivo CUANDO el administrador confirma la baja (BR_009).

**Descripción:**

   El proceso de baja lógica:
   
   1. Actualiza ``status = 'INACTIVE'``
   2. Registra ``deactivated_at = NOW()``
   3. Registra ``deactivated_by = ID del admin``
   4. Registra ``deactivation_reason = motivo ingresado``
   5. Actualiza ``updated_at`` y ``updated_by``
   
   **Baja Lógica (BR_009):**
   
   El registro NUNCA se elimina físicamente. Solo se marca como
   inactivo para preservar integridad referencial e histórico.

----

3. Criterio de Aceptación
-------------------------

::

   DADO validaciones exitosas y confirmación del admin
   CUANDO se ejecuta la baja
   ENTONCES el estado cambia a INACTIVE
   
   Escenario 1: Cambio exitoso
   DADO usuario activo con baja confirmada
   CUANDO se ejecuta el cambio
   ENTONCES status = 'INACTIVE'
   Y deactivated_at tiene fecha/hora actual
   Y deactivated_by = ID del admin
   
   Escenario 2: Motivo registrado
   DADO motivo = "Renuncia voluntaria"
   CUANDO se completa la baja
   ENTONCES deactivation_reason = "Renuncia voluntaria"
   
   Escenario 3: Registro preservado
   DADO usuario dado de baja
   CUANDO se consulta la BD
   ENTONCES el registro existe completo
   Y solo el status cambió a INACTIVE
   Y datos históricos permanecen intactos
   
   Escenario 4: Username reservado
   DADO username "juan.perez" dado de baja
   CUANDO se intenta crear nuevo usuario con mismo username
   ENTONCES se rechaza como duplicado (username nunca se reutiliza)

----

4. Reglas y Restricciones
-------------------------

- **BR aplicables:**
  - BR_009: Solo bajas lógicas, nunca DELETE físico
  
- **CNST aplicables:**
  - CNST-002: Gestión de datos en BD

**Integridad Referencial:**

Las tablas relacionadas (auditoría, sesiones, asignaciones) mantienen
referencias al usuario dado de baja para histórico completo.
