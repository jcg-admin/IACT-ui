2. Especificación
-----------------

**Declaración:**

   El sistema DEBE recalcular los permisos efectivos del usuario
   CUANDO se revocan funciones, mostrando preview antes y aplicando
   después de confirmar.

**Descripción:**

   Dos momentos de cálculo:
   
   **Preview (antes de confirmar):**
   
   1. Toma funciones actuales
   2. Resta funciones a revocar
   3. Muestra comparativa: permisos actuales vs resultantes
   4. Destaca permisos que se perderán
   
   **Aplicación (después de confirmar):**
   
   1. Invalida caché de permisos del usuario
   2. Recalcula permisos desde funciones restantes
   3. Actualiza token/sesión si es necesario
   4. Próximo request usa nuevos permisos

----

3. Criterio de Aceptación
-------------------------

::

   DADO funciones seleccionadas para revocar
   CUANDO el sistema muestra preview
   ENTONCES indica claramente qué permisos se perderán
   
   Escenario 1: Preview de pérdida de permisos
   DADO usuario con REP-001, REP-002, USR-001
   CUANDO se selecciona revocar REP-001
   ENTONCES preview muestra:
      - REP-001: SE REVOCARÁ
      - REP-002: Se mantiene
      - USR-001: Se mantiene
   
   Escenario 2: Permisos que se pierden
   DADO función REP-001 otorga permiso "ver reportes"
   CUANDO se revoca REP-001
   ENTONCES preview indica "Perderá acceso a: Ver Reportes"
   
   Escenario 3: Aplicación inmediata
   DADO revocación confirmada
   CUANDO se completa
   ENTONCES caché de permisos se invalida
   Y siguiente llamada a /api/reports retorna 403
   
   Escenario 4: Usuario con sesión activa
   DADO usuario navegando en módulo de reportes
   CUANDO se le revoca REP-001
   ENTONCES al siguiente request ve mensaje "Sin permiso"
   Y es redirigido a pantalla permitida

----

4. Reglas y Restricciones
-------------------------

- **BR aplicables:**
  - BR_006: RBAC Flat NIST
  
- **CNST aplicables:**

**Caché de Permisos:**

Si se usa caché Redis para permisos, debe invalidarse
inmediatamente al revocar funciones.
